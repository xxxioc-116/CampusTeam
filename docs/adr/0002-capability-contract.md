# ADR 0002 推荐能力契约与配置追踪

- 状态：Proposed，已本地实现与测试，待小组评审确认
- 日期：2026-10-27
- 关联：#13、#14、#15、#18、#27

## 问题

前端采用 0–100 能力自评，原后端只有技能熟练度 1–5；没有可信规则可把技能直接映射成五维能力。
同时需要避免重复能力被算成互补，并保证前端分项解释与后端得分一致。

## 决策

1. API 五维能力使用 0–100，算法内部归一化到 0–1。缺失按 0 保守计算，非法输入明确拒绝。
2. 团队逐维取最大值；缺口为 max(需求−当前,0)；候选人只计超过当前值且位于缺口内的增量。
3. 推荐画像与团队需求单独持久化，不从 UserSkill 猜测能力；保留原表，由团队进一步统一技能来源。
4. 默认权重保持 ADR 0001；仅队长或管理员可保存团队自定义权重。校验五项和为 1，配置摘要随响应返回。
5. 解释同时包含能力填补、其他非零得分贡献与信息不足风险。展示理由与真实分项一致。
6. 每次查询从最新成员关系计算；不缓存能力聚合，以保证审批加入后立即更新。

## 备选与代价

- 平均值聚合：会因低分新成员加入而降低团队能力，不适合当前“有没有人具备能力”的产品定义。
- 求和聚合：会因重复技能和人数增长产生虚假的缺口填补。
- 由技能推断能力：需教师或团队确认映射和测量方法；当前数据不足，容易混淆“技能等级”和“能力维度”。
- 当前最大值模型不能估算工作量、协作成本或人数需求，后续须另建模型。
- 请求时计算只保证当前状态一致，不支持历史推荐重放；有审计需求时需保存完整输入与成员快照。
- 自定义权重只表示可配置，不代表已用用户数据校准；上线默认仍为基线。

## 验证

人工算例、异常/缺失值、重复能力、权重改变排名、字段顺序不改变配置标识、非法配置不覆盖旧配置、
申请/邀请审批后重算、真实浏览器页面回显均纳入测试。数据契约与 API 示例见 docs/api.md。
