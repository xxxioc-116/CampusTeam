### 关键设计决定

1. **五维推荐**：能力互补、技能、时间、目标和经验分别计算 0–1 分项，再按配置权重加权。公共 API 使用 0–100，算法内部归一化为 0–1，避免显示口径与计算口径混用。
2. **稳定 Top-K**：总分降序后以候选人 ID 作为确定性次序；`K=0` 返回空结果，超过候选数自动截断，非法权重和非法数值直接拒绝。固定输入、权重和随机种子可复现相同排序。
3. **解释与得分一致**：响应同时给出分项得分、加权贡献、实际补齐能力、理由和风险；总分来自分项贡献求和，解释不能脱离评分公式单独生成。
4. **请求时重算**：推荐结果基于最新团队成员、候选画像和团队需求即时计算，不保存容易过期的 `MATCH_RESULT` 快照；接受申请或邀请后再次读取矩阵即可看到能力变化。
5. **业务权限**：管理员授权只认 `User.Role.ADMIN`；Django `is_staff` 不等于业务管理员。团队数据读取允许成员、队长和业务管理员，需求写入仅允许队长或业务管理员。
6. **质量门禁**：backend、frontend、真实 integration 三个 job 独立执行，聚合 `quality-gate` 使用 `always/needs`，任一上游失败都会阻止主线合并。

### 反思

- 最初的集成分支包含较多依赖分支内容，增加了归属判断和 Review 成本；后续通过同步已合并基线、删除重复前端差异和单列联调/CI 文件，将 PR #33 收敛到可独立审查范围。
- SQLite 的固定查询数和本地耗时只能证明当前回归性质，不能代表 MySQL 生产 SLA；若继续演进，应在目标数据库上建立统一硬件基线。
- 当前推荐采用内存内线性扫描，适合课程项目规模；候选池继续扩大时需要增加召回层、离线索引或缓存，并明确数据更新一致性。
- 权限判断必须围绕业务角色和对象关系建模，框架字段（如 `is_staff`）不能未经契约确认直接成为业务授权旁路。
